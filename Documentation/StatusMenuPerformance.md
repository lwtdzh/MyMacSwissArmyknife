# 状态栏菜单卡顿排查记录

2026-11-08，在运行了约 12 天的 MyMacSwissArmyknife 1.0 build 41 上采集线程栈。采集和定位期间保留了原进程。

点击图标时，主线程停在以下调用链：

```text
AppStatusMenuController.menuWillOpen
  → makeClipyMenu
    → makeMenuItem
      → ClipyMenuItemSnapshot.displayImage
        → ImageIO PNG 解码
```

当时 Clipy 的菜单快照约 53 MB，包含 3012 个菜单节点和 72 张图片。部分菜单图片的底层像素仍达到 3820 × 1554，而菜单只需要显示一个小缩略图。

旧实现每次打开主菜单都会同步读文件、解码 JSON，并重建 Clipy 子菜单。`requestSnapshot` 中发布快照会触发一次重建，`menuWillOpen` 随后又主动重建一次。收到辅助程序的新快照还会再次刷新。剪贴板历史增加后，这些操作会占用更多主线程时间，菜单需要等它们结束才能出现。

修复后：

- 文件读取、JSON 解码和缩略图准备在专用串行队列执行，连续读取请求会合并。
- 相同快照不重复发布；相同图片和显示尺寸复用已准备好的缩略图。
- Clipy 导出菜单实际需要的像素，最多 512 像素；主程序也能缩小旧版快照中的大图片。
- 主菜单打开时复用已有子菜单，只更新勾选状态。
- 展开的菜单保持稳定，新快照在菜单关闭后应用。
- Combine 回调直接使用传入的新值，避免在 `@Published` 赋值完成前读取旧值。

用保存下来的同一份现场快照，分别编译原实现和修复实现，调用真实的 `menuWillOpen` 五次：

| 测量项 | 原实现 | 修复后 |
| --- | --- | --- |
| `menuWillOpen` 单次耗时 | 1419～1685 ms | 0.001～0.010 ms |
| 控制器初始化 | 1355 ms | 35 ms |
| Bridge 初始化返回 | 130 ms | 0.075 ms |

表中测量的是程序回调耗时。系统绘制菜单和动画的耗时需要通过实际图标点击另行检查。

验证通过了 71 项主程序测试和 3 项 Clipy Bridge 测试，覆盖后台慢读取、重复快照、菜单展开期间更新、勾选状态、图片尺寸和快照兼容性。动作发送测试使用记录型通知中心，避免测试命令发送到用户正在运行的 Clipy。

线程采样、原版应用、设置和现场快照保存在本机私有临时目录 `/private/tmp/mmsak-menu-diagnostic-20261108`。仓库中的测试使用生成的数据。

修复版 build 42 已安装到 `/Applications/MyMacSwissArmyknife.app`，Release 构建和签名检查通过。安装后的快照为 1,286,160 字节，仍包含 3012 个菜单节点和 72 张图片，图片最大边长为 200 像素。

切换版本后发现缩略图磁盘缓存为空，使用保存的现场快照恢复了 53 项缩略图缓存。恢复过程以只读方式打开剪贴板数据库，再让新版辅助程序重新读取缓存索引。

本次未进行实际鼠标点击的显示延迟计时。原始现场数据的回调耗时对照、自动化测试和安装后快照检查均已完成。

正式发布版本为 build 43，主程序与 Finder 扩展使用同一版本号。
